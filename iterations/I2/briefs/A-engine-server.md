## Build

**1. Rules (pure, each with vitest tests)**
- `rules/planOps.ts`: `validateOps(snapshot, ops): string[]` (errors like `"op 2 (rewire WI-004): input slot WI-003/notes-cxo does not exist"`), `applyOps(defs, ops): { defs: ItemDef[]; added: ItemId[]; changed: ItemId[]; cancelled: ItemId[] }`, `describeOp(op, defs): string` (readable line: `"Add WI-004 Consolidate themes under PH-2 (agent), inputs: WI-003/notes-ceo, …; output: themes (md); gate: human review"`). Snapshot = defs + status per item + the set of slots that have versions. Rules: add_item id unique, parent must be ENG/composite/null, executor agent|human for a leaf; update_brief on a leaf only if waiting/ready (ENG/composites always); rewire only waiting/ready and every slot must exist (plan or same proposal); add_slot name unique in item; remove_slot not if it has versions or consumers; set_gate only `[]` or `[{type:"human-review"}]`; cancel_item only waiting/ready and no non-cancelled consumer; **no cycles** in producer→consumer + sequencing graph; ops apply in order (later ops see earlier ones).
- `rules/readiness.ts`, decision **D1**: a required input counts only if published **and** (its producer has no gate **or** the producer is `done`). ENG and composite producers: published is enough. The new blocker is `{kind:"input_not_approved", slot, producer, status}`. Update the scheduler call site.
- `rules/lifecycle.ts`: add a `cancel` event (waiting|ready → cancelled), and `answer_overridden` (ready|at_gate → in_progress). Treat `run_ended` with outcome `completed` as denied (Approach-only outcome).

**3. Server services** (new modules, for example `approachService.ts`, `proposalService.ts`, `questionRouting.ts`, `approachPort.ts`, `briefing.ts`):
- **Approach runtime wiring**: in `engagementContext.ts` add `approachRuntime` (`createFakeApproachRuntime({})` / `createSdkApproachRuntime(sameConfigAsWork, workspace)`, both exported from `@workbench/agents`; they are stubs until B lands, so your tests inject their own scripted `ApproachRuntime`). Keep Approach runs **out of `ctx.activeRuns`** (keyed by item, counts toward autostart concurrency); add `ctx.approachRuns`. Approach runs are rows in `runs` with `itemId "ENG"`, reason aa-*, model = current profile's `models.approach`; activity goes to `paths.runActivity(runId)` and is pushed with `threadId`; `RunStarted`/`RunEnded` carry `threadId` for turns.
- **Threads/turns**: every engagement gets thread `T-0001` ("Engagement conversation") at creation; create it lazily for I1 engagements. `postMessage(ctx, tid, text)`: 409 conflict if a turn is running; persist the human ChatMessage (+`ChatMessagePosted`); lease `aa-thread:T-0001`; situation = the full **briefing** if `thread.sessionId` is null, else `"Since your last turn:"` plus ≤ 20 readable event lines since `lastSeenSeq` (or ""); `approachRuntime.startTurn`. `onSession` stores `thread.sessionId`. On end: post an `approach` ChatMessage with `result.lastMessage` (if non-empty), set `lastSeenSeq`, release the lease. **Briefing** (deterministic, no LLM): engagement name + settings; plan at depth 2 with status, executor, inputs, outputs + latest versions, gate; open requests; pending proposals.
- **ApproachPort** (`approachPort.ts`, bound per run): `getPlan` → PlanDigest (Markdown text + `suggestedNextIds`); `getItem`; `proposeOps` → validate against the current plan; on errors return `ok:false` and create **nothing**; else create proposal (base = current planVersion, author `approach:<sessionId or runId>`, origin conversation with threadId, or suggestion with `suggestedBy` + `requestId`), supersede the same thread's pending proposal (`ProposalSuperseded`), post a system ChatMessage with `proposalId` in T-0001, `ProposalCreated`; for a suggestion session also resolve the suggestion request (`kind:"suggestion", outcome:"proposed"`). `answerRequest`/`escalate` only in question sessions for their own request, `declineSuggestion` only in suggestion sessions (else `WorkPortError("not_allowed")`). `publishEngagementAsset` = `workPort.publishAsset` for ENG (source inside `ENG/work/`, author `approach:<session>`), plus system ChatMessage "Published ENG/context v1.0" with `asset`, then `syncPlanState`. `journalAppend` → server appends to `items/ENG/work/approach-journal.md` (`JournalAppended`). `notifyHuman` → Notification + `HumanNotified`.
- **Question routing** (in `workPort.raiseQuestion`): `always-human` → as in I1 (`to:"human"`, `routedTo:"human"`). `aa-first` → `to:"approach"`, `routedTo:"approach"`, an agenda row (kind question), `QuestionRouted`, enqueue a **task session**. Task sessions run **one at a time** (FIFO, lease `aa-task:<requestId>`). A blocking question's task starts only after the asking item's run has ended (pump the queue after every run end). `startTask` gets the situation briefing, the request and the asking item's def. **AA answer**: resolve the request with `{kind:"answer", mode, text, by:"approach:…"}`; worklog entry "Answered by the Approach Agent: …"; an FYI Notification with `requestId`; if blocking → `question_answered` + `launchRun(resume-answer, answeredBy)`. Refactor `services.answerQuestion` into a shared function instead of duplicating it. **Escalate**: `to:"human"`, `escalation {view, by, at}`, stays open, `QuestionEscalated` (the human answers via the existing J1.4 route). **Task ended without deciding**: escalate with view "The Approach Agent did not decide."
- **Suggestions** (`workPort.proposePlanChange`): request type `proposal`, `to:"approach"`, then enqueue a suggestion task. Decline → resolve `{kind:"suggestion", outcome:"declined", reason}`, `SuggestionDeclined`, worklog note on the suggesting item. Not decided → decline with reason "The Approach Agent did not assess this suggestion." plus an FYI.
- **Override** (`POST requests/:rid/override`): only for a question answered by `approach:*`, and only when the item has no active run and its status is ready or at_gate. At_gate: withdraw the open gate request/round. Then replace the response (by human), apply `answer_overridden`, `launchRun(resume-answer)`.
- **Proposals**: approve → check pending and `basePlanVersion === meta.planVersion` (else reject with the reason "The plan changed since this proposal …"); apply per this order: validate, write `item.md` files (`writeItemMd`; cancelled leaves get status cancelled via the rule), upsert the DB index + statuses for new leaves (waiting), bump planVersion (engagement.yaml + DB meta), `ProposalApplied` + `PlanChanged`, checkpoint commit then `git tag plan/vN`, `syncPlanState`. Reject(reason) → `ProposalRejected` + a system ChatMessage (the agent sees it in its next delta). `previewProposal` → `PlanPreviewView` built from `applyOps` over the current defs (nothing written). `editItem` (J1.7) also emits `PlanChanged{cause:"edit"}`.
- **Settings/profile**: `PATCH settings` writes engagement.yaml, `SettingsChanged`, reloadMeta; `createEngagement` accepts `settings` overrides. Profile: `GET/PATCH /api/profile` stores `{profile}` in `<workspace home>/.workbench/settings.json`; every **new** run (work and approach) reads the current profile at launch (J2.8); running sessions keep theirs.
- **Views/routes**: every new route in `api.ts`. Inbox adds `proposal` (pending) and `fyi` (undismissed, with `override: Allowed`). Routes contain no logic.
